# Kira's AI Workflow Guidance

> 约束人与 AI 的交互，让产出可控、可审、可撤回，而不是不可收拾的屎山。

[toc]



---

## 使用 AI 前

### 想清楚你要干什么

开口之前，先把任务收成「可执行的合同」，而不是一句模糊愿望。

- **定义清晰问题边界**：要解决什么、不解决什么、允许动哪些范围。
- **自己尝试描述任务**：用自己的话写清现状、目标与可见结果；写不清楚就还没准备好交给 AI。
- **分点列出详细需求与行为约束**：验收标准、禁止事项、风格要求等都写成条目。若你自己已有实现方案或具体想法，一并提供给 AI，减少它按「常见最佳实践」乱发明。

### 了解当前项目进展

中途接手或隔了一段时间再动项目时，先建立共享理解，再谈改代码。

- **使用单独 Agent 对话，让 Agent 总结项目**，并明确要求：**不修改当前代码**（只调研、只输出笔记与风险点）。
- **生成或更新 `AGENTS.md`**，让后续 Agent 也能快速了解项目。按需要写入关键信息，例如：如何运行、目录结构、代码风格、安全与代码禁区、已知坑、待确认事项（推测须标成「待确认」，避免假文档）。

### 保护好你的原有代码

在 AI 开始改之前，先保证「改坏了能撤回」。

- 查看要修改的代码当前是否处于 Git 等版本控制系统管理之下。
- 检查当前改动是否已经 commit，或是否需要先 commit，避免 AI 改动与未保存的人工改动缠在一起、无法干净回退。

### 与 AI 一同头脑风暴

> 此子章节用于：自己目前还没有解决方案、不会做、或正在尝试陌生领域时，向 AI 询问方案或意见。

- 使用 Plan 模式，让 AI 给出超出你当前能力边界的解决方案，并不断修改、优化方案。方案阶段的改动范围，以你所用 Agent 框架 / Plan 流程的约束为准。
- **Agent 的 Plan 看不懂怎么办？** 使用网页 AI 查询、解释细节；避免在同一个 Planning 对话里过多、碎片化追问，把规划上下文打散。

### 防止 AI 陷入内耗

很多「AI 在空转」其实不是模型不行，而是环境没就绪：它反复试安装、试联网、试连设备，上下文被失败日志填满，真正任务还没开始。开工前先把外围条件备好。

- **提前安装好开发环境**：编译器、SDK、包管理器、驱动、仿真器等你已知必需的依赖，尽量在开 Agent 之前装好并验证能用；不要把「从零搭环境」和「实现功能」捆在同一对话里。
- **提供可用的网络代理**：需要拉包、查文档、访问外网时，明确告诉 AI 代理怎么用（或已在系统/终端里配好），避免它在超时与重试里空转。
- **确保要调试的设备处于正常状态**：例如已经开机、串口已连上、网络能 `ping` 通、必要的权限与线材无误。设备都没就绪就让 AI「先调通」，几乎必然内耗。
- **提前拉取需要使用的代码**：依赖的开源仓库、厂商 SDK、参考实现等，先由你（或稳定网络环境）clone/下载到本地路径，再在任务里写明路径让 AI 读取；不要让 AI 在对话里反复因网络失败而重试拉取。

## 使用 AI 中

### 合理给 AI 授权

权限默认从紧：能少给就少给，能仿真就别上真机。

- **禁止 AI 控制可运动的硬件**（如机械臂）。把明确的安全要求写进对话，并写入 `AGENTS.md`。优先让 AI 使用仿真、离线测试等。涉及机械臂时，可先抱闸或按下急停，再让 AI 修改代码，防止意外启动。
- **默认拒绝不可逆操作**，并写进 `AGENTS.md` 与当次任务说明，例如：删除数据、对外发送消息/邮件、动真机/生产环境、扩大到需求外的重构。需要做时，必须由你显式确认。
- 优先使用类似「Approve for me」**或你所用 Agent 中等价的自动批准 / 代审执行**能力，在逐步审查中推进。仅在数据已良好备份（如磁盘快照、Git 已推到远端）的前提下，才考虑 full permission、无监督执行。若必须给 root，只通过 `pkexec` 等方式做有限、可审计的提权，不要把长期宽权限当成默认。

### 清晰描述遇到的问题

- 先尝试运行代码；若涉及现实操作（如机械臂相关开发），先做好安全防护（握好急停）再跑。
- 能够清晰描述遇到的问题：**多个问题分开列**，并附上可能原因与已尝试步骤。

### 避免一个对话干多个活

* 过长上下文会拖垮 Agent 的稳定性与注意力。每个独立任务使用单独的上下文（新对话 / 新 Agent 会话）。

* **每完成一个独立任务，先跑你为该任务定下的验证步骤**（编译、测试、仿真、关键路径等），确认无误后再开下一个对话做下一件事。

### AI 做不出我想要的效果

* 不要在已经混乱的超长对话里硬磨。开启新上下文，重新梳理当前框架与现状，分析问题原因，再继续修改。

## 使用 AI 后

### 进行 Code review

- 检查更改内容，查看代码可读性。
- 检查功能是否完成，是否达到设计要求。

### 及时维护文档

- 让 Agent 维护 `README`、`AGENTS.md`（以及其他你项目约定必须同步的说明），使下一轮接手的人与 Agent 仍有同一份真相来源。

### 提交 Git 代码

- 完成审查与文档更新后，再 Git 提交、推送（可由 Agent 使用 `gh` CLI 等工具协助；推送与否按你的仓库习惯，需要时由你确认）。

## 附录：可复制的任务开场模板

```text
【项目简介】（接手代码、中途开场）
这是一个xx系统/xx的SDK，其中xxx是干啥的，xxx是干啥的
【目标】
现在，我需要基于此实现一个xxx的系统。
【需求与行为约束】（分点）
1. xxx需要如何设计
2. xxx要实现什么样的功能
3. xxx是干啥用的
【我已有的方案/想法】（可选）
1. xxx可以这样做
2. xxx可以参考开源仓库xxx的实现（手动拉取仓库后再让ai读取，防止因为网络问题内耗）
3. 我认为xxx这样设计会更好
【参考】
1. 我已经拉取xxx仓库到<PATH>
2. 这是我的xxx机械臂的官方SDK以及ApiReference
3. 需要参考这份说明书/文档/论文
4. 可以使用xxx的方式使用网络代理
【约束】
要做：
1. 维持xxx的代码风格
2. 在一个名为xxx的文件下写
3. 创建一个名为xxx的新模块并再其中编写
不做：
1. 改动其他不相关文件
2. 改变已有xxx模块的实现
【授权与禁区】
- 禁止：可运动硬件实控 / 删数据 / 对外发送 / 动真机或生产……
- 允许：使用pkexec获取root权限、仿真、只读调研、在已批准范围内改代码……
```
